# 常见问题与设计说明

## 一、手上有三四个智能体，经验散在各处，怎么搭起来

以「Claude Code + Codex + Cursor + 网页版 ChatGPT」为例：

| 步骤 | 在哪做 | 做什么 |
|---|---|---|
| 1 | 任意一个能运行命令的智能体（比如 Claude Code） | 安装 skill，说「帮我建一个反馈经验库」，并选库放哪。默认接入可检测到的智能体、回溯近 30 天对话，语言跟随用户。可在汇集前指定范围。 |
| 2 | 同上 | 建库 → 给检测到的智能体写入路由块 → **首次汇集**：把每个智能体自带的规则和记忆，比如 `CLAUDE.md`、Claude 的自动记忆、`~/.codex/AGENTS.md`、Codex 的 memories、`GEMINI.md`、Cline 和 Roo 的 rules，都复制进投放区，并回溯过去 N 天的对话 |
| 3 | 你自己 | 把手上已有的规范、SOP、笔记（Word、PDF、Excel……）直接拖进 `投放区/` |
| 4 | 第一次维护（自动或手动触发） | 维护者把投放区的文件统一转成 MD，从各智能体的旧规则、旧记忆和旧对话里**只提炼你的反馈和标准**，合并重复的，归到对应分支。材料多的话会分几轮或几天处理完 |
| 5 | Cursor | Cursor 的全局规则存在应用设置里，没法自动写入：粘贴一次 `fm export --all` 的输出；在具体项目里用 `fm sync --project <项目目录>`，Cursor 会读项目里的 `AGENTS.md` |
| 6 | 网页版 ChatGPT | 运行 `fm export --all`，筛选后把所需内容粘进自定义指令。标准更新后要重新导出。 |
| 7 | 以后在 Codex 里第一次用到时 | 不需要再装 skill，路由块已经告诉它库在哪、怎么读写。想让 Codex 也能负责安装、维护这类操作时，再给它装 skill，然后说「加入接力」即可（`fm join --agent codex`） |

**其他智能体怎么知道有这个库？** 靠路由块：`sync` 或 `join` 把一小段说明写进每个智能体的全局配置（比如 `~/.codex/AGENTS.md`），每次对话都会加载。里面写着：库在哪、本机工具在哪、怎么读、怎么写、有哪些分支。

**每个智能体都要装 skill 吗？** 不用。读写只需要路由块，加上本机工具 `~/.cy-feedback-memory/tool/`。skill 只是让某个智能体能主动帮你做安装、维护、体检这些操作。

## 二、多个智能体一起写，会遇到的问题和对策

| 问题 | 会发生什么 | 怎么处理 |
|---|---|---|
| 两个智能体同时写同一个文件 | 后写的覆盖先写的 | `fm add` 先加文件锁再写，写的时候先写临时文件再替换。共享盘上也能用 |
| 同一句反馈被记了好几次 | 你在 A 里说了一句，A 当场写进库，第二天维护时又从对话记录里抽出来一次 | 已经直接写进库或收件箱的原话，抽取时会自动跳过；标准相同就把〔×N〕加一，不会新增一行 |
| 各智能体写入的质量参差不齐 | 有的写成死规定，有的放错了层，有的把自己的推测写了进去 | 写入必须走工具，格式统一。每次维护，值班的智能体会逐条复核上次维护以来别人的直接写入，最后再跑一遍检查 |
| 几个智能体都设了定期维护 | 同一份材料被处理好几遍，花双倍 token | 维护时加锁，并记下当天已经维护过：第二个来的会直接收到 LOCKED 或 ALREADY-DONE 然后结束 |
| 维护期间又有智能体写入 | 和维护者改的内容冲突 | 维护进行中时，`add` 自动改记到收件箱，留到下一次维护处理 |
| 新旧要求冲突 | 上个月说 5 行，这个月说 3 行 | 同一个〔键〕的新说法替换旧说法，旧的进归档并注明原因。先核对谁说的、对哪个客户/项目、什么条件下：同一范围的标准变了才以新替旧；某个客户的例外写进它自己的分支，不改通用标准；同期同范围矛盾才放进「待验证」。维护者全程自己判断，不打断你，改动写进维护记录，可用快照撤销 |
| 智能体自带的记忆还在写 | Claude、Codex 都有自己的记忆，两套并存 | 每次维护都会把它们的新内容汇集进来（只收有变化的）。`doctor` 会提醒你，也可以直接关掉它们自带的记忆 |
| 网络盘或同步盘掉线 | 库找不到，命令报错 | 工具每台电脑本地都有一份；写不进库时先记在本机，下次维护时自动合并 |
| 多台电脑上的路径不一样 | Mac 是 `/Volumes/盘`，Windows 是 `Z:\` | 路由块是每台电脑各写各的，每台电脑运行一次 `init <本机看到的路径>` 加 `sync` |
| 工具版本不一致 | A 电脑的 skill 新，B 电脑的旧 | 库里放一份工具，各电脑运行 `sync` 时会同步到本机；库的格式比工具新时，旧工具拒绝写入，并提示升级 |
| 改坏了想恢复 | 维护者误删、误合并了内容 | 每次维护前自动在 `.fm/snapshots/` 保存快照，保留最近 14 份。用 Git 管理实际经验库时选私有仓。 |
| 不知道谁改了什么 | 出问题时没法追查 | 接力日志 `fm journal` 记录每一次写入：谁、什么时候、写了什么；`维护记录.md` 记每天的维护 |
| 路由块越来越大 | 每次对话都加载，token 越花越多 | 超过上限时 `lint` 会提醒；核心约定最多 12 条；分支超过 15 条或 4000 字时按主题原样拆成子分支（`fm move`），不删减、不改写——准确优先于省额度 |
| 敏感信息 | 对话、原件或日志含需要限阅的内容 | 限制采集范围和访问权限，整理前先筛选材料。云端模型可能接收读到的内容，自动脱敏只覆盖部分材料。[采集范围和隐私](agents.md#采集范围和隐私) |

## 三、用户直接放进去的文件

- 放进 `投放区/`（或者用 `fm import <路径>`）。放进某个分支目录下也可以。
- 维护时会自动转成 MD：Word、PPT、Excel、网页、CSV、JSON、TXT 用内置的转换（只用标准库）；本机装了 markitdown、pandoc、pdftotext 或 textutil 的，会借用它们转更多格式。
- 转不了的（没有 PDF 工具时的 PDF、图片），交给维护者读出内容，写成同名 `.md`。
- 原件一律移到 `.fm/originals/日期/`，不会删除。
- 转好的 MD 只提炼其中的反馈和标准：整份值得留的，移进对应分支的 `文档/` 并在「资料」段加一条链接；其余移进 `归档/已处理的投放/`。
- 在投放区放了 3 天以上还没处理的文件，`lint` 会提醒。

## 四、为什么这样设计

- **只存反馈**：事实和进度会过期，而且各个智能体自己就能查到；你的判断标准没人能替你查。
- **对话中尽量少写**：每轮只自查一次：有纠正、拍板、认可或已验证的结论才写一条，而且不读库；漏的由维护从对话记录补收；其余交给定期维护：每周固定一次（额度刷新前 1 小时，用本来要作废的剩余额度），平日积压超过阈值才提前；判断都由脚本做，没有新内容就不调用模型。
- **人人能写，一人值班**：写入可以分散，整理必须集中，不然几个智能体会各自整理、互相打架。
- **分「只这次 / 以后都这样 / 待验证」**：把一次性的改法当成永久规则，会把智能体训得越来越死板。
- **纯 Markdown**：编辑器可以直接读写条目和文档。分支的新增、移动和归档走 `fm`，编辑后用 `fm lint` 检查格式。
